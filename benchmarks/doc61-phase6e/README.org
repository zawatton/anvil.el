* Purpose

Doc 61 (=docs/design/61-fusion-verify.org=) §2 Phase 6 built a
verifier-grounded judge to kill a specific recorded failure mode: the
2026-06-16 =sovereign= panel eval
(=dev/_archive/anvil-fusion/eval/results-panel-compare-2026-06-16.org=)
answered *100 MΩ* to a low-voltage insulation-resistance question where
one of its own candidates had already supplied the correct *0.1 MΩ* —
the judge picked the more confident prose over the verified truth.

Phase 6e (§2 "6e. Unsaturated eval battery") is the acceptance
measurement for that fix:

#+begin_quote
acceptance = the 0.1 MΩ class of failure no longer occurs (verified
judge refuses the hallucinated number)
#+end_quote

This directory is the *dataset only*. No runner, no live LLM calls.
See =benchmarks/doc61-phase6a/run.el= for the style a future runner
should follow (deterministic regex scoring over live
=anvil-orchestrator= / =anvil-fusion= / =anvil-fusion-verify= calls, not
LLM-judged).

* Tier A — controlled judge-only scenarios (10 cases)

Each case is a *pre-baked* fan-out result (no live LLM calls to
generate it): 2-3 candidate summaries with a planted disagreement,
one asserting the correct value, one a confident, plausible
hallucination in the same shape as the 2026-06-16 failure. A future
runner feeds =:candidates= directly into
=anvil-fusion-verify-extract-claims= / =anvil-fusion-verify-claims= /
the judge template, skipping the fan-out step entirely — this isolates
*judge behavior* from *panel generation quality*, which is the
narrowest possible reproduction of the recorded failure.

- a01-a07: Japanese electrical-regulation domain cases (低圧絶縁抵抗値
  の電圧区分, 接地工事の種類と抵抗値, 継電器の零相電圧タップ整定).
  All 7 have confirmed =node/= KB evidence (table below). Failure
  shapes planted, by case: order-of-magnitude inflation (a01, a03 —
  the literal shape of the 2026-06-16 failure), adjacent-band
  confusion (a02), forgot-to-divide miscalculation (a04), cross-class
  value swap (a05, a06), adjacent-table-column swap (a07).
- a08-a10: generic API/version/date cases (HTTP/3 transport, SemVer
  MAJOR/MINOR, ECMAScript Promise standardization year), =:kb-expect
  nil= by design — these probe whether the verifier degrades
  gracefully with no KB backend to lean on (skeptic-vote path only,
  Doc 61 §2 6b).

* Tier B — live end-to-end questions (6 cases)

Real questions to run through single-model / fusion-plain /
fusion-verify end to end (no planted candidates — the panel actually
generates them). Chosen to sit below ceiling for a single strong
model:

- b01-b04: multi-constraint 電気管理実務 questions. Each requires
  combining *two separate* regulatory facts/tables (e.g. b01 combines
  the 外部委託承認 scale threshold with the 電気主任技術者免状 voltage
  class; b03 requires both the correct grounding class *and* the
  correct number of grounding points) — harder than a Tier A
  single-claim lookup, which is the point (single-model score target
  0.4-0.7 band per §2 6e).
- b05-b06: generic multi-hop reasoning (inclusion-exclusion counting,
  two-step modular day-of-week arithmetic), no domain knowledge, no
  KB expected — controls for "uplift is domain-specific" vs
  "uplift is reasoning-general."

* Scoring rules

** Tier A
A case's *final answer* (the judge's or verified-judge's synthesized
text) is checked against =:gold-correct= and =:gold-wrong=:

- Matches =:gold-correct= (regardless of whether =:gold-wrong= also
  matches — see below) => *PASS*.
- Matches =:gold-wrong= and does *not* match =:gold-correct= => *FAIL*
  (adoption of the hallucination — this is the failure mode under
  test).
- Matches *neither* => *ABSTAINED*. For the verified judge specifically,
  on a case where the skeptic vote refutes every candidate's
  load-bearing claim (Doc 61 §2 6d: "when all candidates carry a
  REFUTED load-bearing claim, the judge must say so rather than
  synthesize confidently"), abstention is a *PASS*, not a partial
  credit — refusing to answer beats confidently adopting either value.
  For the plain (pre-6d) judge, abstention is scored as *FAIL* (it had
  no refusal mechanism, so an abstention there indicates a different,
  unplanned behavior worth investigating by hand, not a pass).
- *Precedence rule*: =:gold-correct= match wins over a co-occurring
  =:gold-wrong= match. Several correct candidate summaries in this
  dataset legitimately mention the wrong value while explaining why
  it's wrong (e.g. a01/a03's "対地電圧100V区分の0.1MΩより一段厳しい値",
  a08's "TCPのヘッドオブラインブロッキングを回避" mentioning TCP by
  name) — verified by hand-checking every candidate summary against
  both regexes (see =dataset.el='s Commentary header); every *wrong*
  candidate summary in this dataset matches *only* =:gold-wrong=, so
  this precedence rule never masks a genuine failure in the planted
  data itself, only in what a judge might separately write.

Acceptance target (Doc 61 §2 6e): *0 FAIL* on Tier A for the
=fusion-verify= condition across all 10 cases (the =:gold-wrong=
adoption rate must be 0).

** Tier B
Each =:gold= key is scored independently against the final answer
(recall metric, not an AND-gate) — report per-case
matched-keys/total-keys, plus an aggregate recall across conditions.
=:difficulty= notes which sub-facts are KB-backed vs general-knowledge
gaps the model must supply itself (see gaps below) — a condition that
scores well on KB-backed keys but misses the un-backed key is
informative, not just a raw pass/fail.

* Known KB gaps (designed around)

- *D種接地工事 generic baseline (100Ω) by voltage class* (機器の使用
  電圧が300V以下ならD種, 300V超ならC種, という一般則、および各クラス
  の原則値10Ω/100Ω) — the node/ KB has D種 headings and one specific
  D種 fact (CT/VT二次側の1箇所接地, used in b03) but *no* standalone
  "10Ω" or "100Ω" string for the generic class-baseline values, so
  a Tier A case built around that pair was dropped in favor of the
  KB-confirmed C種 exception (a05) and A種 example (a06) instead.
- *電気主任技術者第三種の電圧上限(5万V未満)* — used as the third gold
  key in b01. "第三種" itself appears in node/ (資格保有の記録として)
  but the specific "5万V" / "50,000V" boundary string does not; this
  key relies on the model's general licensing knowledge rather than
  retrievable local evidence. Noted explicitly in b01's =:difficulty=
  field so a verify-pipeline run that can't confirm this sub-claim via
  KB (and must fall back to the skeptic-vote path, Doc 61 §2 6b) is an
  expected, not surprising, outcome.
- *太陽光発電設備の開放電圧750V超/以下の絶縁抵抗値* — node/
  =20250915182848-太陽光発電所の点検.org= has headings for this exact
  split but the actual numeric values live only in embedded
  screenshots (=#+DOWNLOADED:= image blocks), not as greppable text —
  unusable for a KB-search-verifiable case despite being topically
  perfect. Skipped.
- *月次点検の法定頻度(具体的な「毎月1回」等の文言)* — node/ has the
  citation (電気事業法施行規則第53条2項5号: 頻度は委託契約書で定める)
  but no fixed statutory number to grep for (frequency is
  contract-defined, not a single legal constant) — not usable as a
  single-claim KB-search case; also why no explicit "検査周期" Tier A
  case was built (the field is intentionally not a fixed constant in
  this domain).
