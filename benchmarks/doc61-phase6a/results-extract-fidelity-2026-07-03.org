* Failure notes (raw claim lines quoted)

** haiku collapses two-sided disagreements into one side (cases 2, 6, 7)

The characteristic haiku failure is NOT format damage — it is merging
a planted A-says-X / B-says-Y disagreement into a single claim
carrying only one side (sometimes with wrong candidate attribution):

- case 2: =CLAIM: 300Vを超える低圧用機器の金属製外箱の接地工事の種類はC種である | KIND: fact | CANDIDATES: cand-A,cand-B=
  — cand-B actually said D種; the D種 counter-claim was never
  extracted, and the attribution is wrong.
- case 6: =CLAIM: Python 3.12 was released in 2023. | KIND: number | CANDIDATES: cand-A,cand-B,cand-C=
  — cand-B's "2022" side disappeared entirely (attributed the
  majority value to all three candidates).
- case 7: =CLAIM: HTTP/1.1 introduced true multiplexed streams over a single TCP connection | KIND: fact | CANDIDATES: cand-B=
  — kept only the minority (wrong) side; the HTTP/2 majority claim
  is implied but absent.

This matters for Phase 6b: a verifier can still refute the extracted
one-sided claim, but the "which candidate said what" map — the input
the grounded judge needs — is degraded.

** sonnet's one big miss: false NONE (case 8)

sonnet output the literal =NONE= for en-api-name despite the planted
pathlib-vs-os.path contradiction (raw: ="NONE"=).  Recall damage
equal to two haiku one-side merges, and arguably worse for 6b (the
disagreement is invisible rather than half-visible).  haiku extracted
both sides of this case cleanly (kind mislabeled fact vs code, text
correct).

** Both models fail the NONE control (case 5)

Neither model output =NONE= on the no-contested-claims control; both
promoted paraphrase-level differences to "contested claims":

- haiku (2 spurious), e.g. =CLAIM: 月次点検を外部の業者に委託して実施することができる | KIND: fact | CANDIDATES: cand-C=
- sonnet (3 spurious), e.g. =CLAIM: 電気主任技術者の指揮監督の下で点検を実施する者は「点検員」という特定の役割を持つ人物である。 | KIND: fact | CANDIDATES: cand-B=

False-positive behaviour is a *prompt-level* issue
(`anvil-fusion-verify-extract-template' criterion (b) "単一の候補のみ
が述べている…重要な主張" invites this), not a model-tier issue.
Verification cost in 6b is capped by `anvil-fusion-verify-max-claims'
anyway, but the template's "single-candidate load-bearing claim"
criterion deserves tightening regardless of model choice.

** Kind labels drift between fact/number/code (both models)

- haiku case 8: both pathlib/os.path claims recalled but labeled
  non-=code= (0/2 kind).
- sonnet case 6: both 2023/2022 claims recalled but labeled
  non-=number= (0/2 kind).

The parser's normalization (unknown kind -> =fact=) absorbs this;
Phase 6b should not branch hard on :kind.

* RECOMMENDATION

*haiku-class is sufficient for the extraction pass* under Doc 61
section 9's criterion (recall within ~10% of sonnet-class, no format
collapse):

1. Recall gap is 7 points (79% vs 86%), inside the ~10% bar — and
   sonnet's advantage is not uniform: sonnet's single false-NONE
   (case 8) is a worse failure mode for 6b than haiku's one-sided
   merges, which at least surface the contested topic.
2. Zero format damage in 16/16 calls: every response was either
   well-formed =CLAIM: ... | KIND: ... | CANDIDATES: ...= lines or
   the literal =NONE= sentinel.  The weakdistill "weak models mangle
   structure" concern did not reproduce at haiku-4.5 tier for this
   narrow, rigidly-templated task.
3. haiku is ~40% cheaper per call ($0.036 vs $0.058 avg); latency is
   noisier but same order (both dominated by child-session startup).

Action: pin =anvil-fusion-verify-extract-model= default to ="haiku"=
(keep `anvil-fusion-verify-extract-provider' = `claude').  Two
follow-ups independent of the model choice:

- Harden `anvil-fusion-verify-extract-template': instruct that when
  candidates disagree, EACH side must be emitted as its own CLAIM
  line with only the candidates that actually asserted it (fixes the
  haiku merge failure and sharpens sonnet attribution too).
- Tighten the NONE criterion (e.g. "paraphrase/emphasis differences
  are NOT contested claims") — both tiers currently over-extract on
  agreeing panels.
