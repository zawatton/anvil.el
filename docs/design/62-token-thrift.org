* 0. Executive summary

anvil.el already ships a token-efficiency layer (Doc 26-29: manifest
tools/list filter, progressive disclosure, intent discovery; Doc 36
auto-compact; anvil-context; longrun O(1) digests; fusion :fidelity summary
clamp). This wave targets the spend that layer does not touch, motivated by
two concrete observations from the 2026-07-03 Doc 61 session:

1. The fusion/verify pipeline itself is expensive at run time (opus-solo +
   verify ~= 4x a single ask; the 6e battery cost $15.01) while the 6e
   measurement showed a strong single model is already saturated on easy
   prompts — paying the multiplier unconditionally is pure waste.
2. Session-side tool traffic is dominated by a few repetitive patterns:
   full test-suite output re-read on every verification round, full file
   re-reads during review cycles, and large tool results consumed whole.

Discipline: measure first (Phase 1), then cut the measured hotspots — the
same evidence-first approach that Doc 61 6e used for verification value.

* 3. Phase 1 — token telemetry (the measurement)

Goal: answer "which tools/flows consume how much" with numbers, per
session, before optimizing anything else.

Design:
- Extend =anvil-server-metrics.el= (NOT a new module): at the dispatch
  seam it already instruments, accumulate per tool-id: call count, total
  request chars, total response chars, max single response, and an
  estimated-token column (chars/4, clearly labeled as an estimate).
- New MCP tool =metrics-token-report=: returns session totals + top-N
  tools by response volume (default N=10) + the same for request volume,
  as a compact table-shaped plist. Optional =reset= parameter.
- Zero overhead goal: counting lengths of strings already in hand; no
  extra serialization passes.
- Non-goal: measuring Claude-side context tokens (invisible to anvil);
  MCP request/response volume is the proxy this phase commits to.

Acceptance: after a normal work session, the report identifies the top-3
volume sources; the numbers drive re-prioritization of Phases 3/8/9 in
this doc (update §2 with findings).

* 4. Phase sketches (2-9, design detail deferred until Phase 1 numbers)

- Phase 2 (router): difficulty probe = claim-extraction disagreement
  density on a haiku pre-pass, or panel-free heuristics (question length,
  domain markers, prior-session verdict cache hits). Escalation ladder
  single -> claude-pair -> opus-solo+verify; thresholds defcustom;
  decision logged for later calibration. Evidence: 6e Tier A saturation
  (plain judge 10/10) vs Tier B uplift (79->100%).
- Phase 3 (test distiller): MCP tool running batch ERT and returning only
  {ran, unexpected, failing test names, first backtrace head}; pattern
  proven manually throughout the Doc 61 session.
- Phase 4 (verdict cache): key = sha1 of normalized claim text + kind;
  value = verdict/evidence/timestamp; TTL defcustom; invalidation on KB
  root mtime change is best-effort. Skips the skeptic batch on hit.
- Phase 5 (sequential skeptics): submit 1 skeptic; escalate to N only when
  the verdict is REFUTED-with-weak-reason or conflicts with KB evidence.
- Phase 6 (numeric-match checker): claim :kind number + KB line containing
  the same number+unit within a small window of the claim's entity terms
  -> confirmed with file:line evidence, zero LLM calls. Follows the 8a
  checker contract (confirm-or-hint only).
- Phase 7 (judge dedup): pairwise Jaccard (already computed for consensus)
  >= threshold -> send representative + unified diff of the others.
- Phase 8 (diff-first read): session-scoped {path -> content hash + last
  body}; re-read returns a unified diff against the cached body. Reuses
  anvil-disk divergence machinery.
- Phase 9 (disclosure budget): any tool response > budget chars returns
  digest + disclosure URI instead of the body; opt-out per tool. Extends
  Doc 28 to a default rather than per-tool wiring.
